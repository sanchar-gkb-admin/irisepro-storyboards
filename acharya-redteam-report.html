Mission Acharya 3-Stream Spec — Red-Team Report

Six independent auditors attacked the spec across coexistence, zero-regression, engine encoding, the refactor blast radius, data integrity, and rollout safety — each verifying claims against the actual code, not the spec's own citations.
VERDICT: GO-WITH-FIXES
The single most reassuring finding: every failure mode is fail-closed. Each gap below makes card generation crash loudly (a clear error, teacher sees "preparing") — no wrong Acharya card, and no altered student card, would ever ship silently. The isolation logic is correct; the concerns are that two core engine mechanisms don't exist yet, some blast-radius is unscoped, and a few guarantees are asserted but not enforced by code. None are unfixable. Fix the must-fix list before writing code.

1 · Must-fix before build (4 critical + 6 high)

CRITICAL

1. The refactor as written breaks ALL online payments

The spec says "replace audience + is_listed with is_institutional" and lists only 2 model scopes. But is_listed is read at 5 unlisted money/provisioning sites (PaymentController:346, PaymentController:1007, EnrolPaymentController:57, DrainHoldingQueue:54, LandingController:558). Drop the column without touching these → !$fallback->is_listed becomes !null===true → every student payment aborts 422 "not payable online"; two queries throw "unknown column" → 500 on the pay-link + holding-queue drain; the webhook stops provisioning explicit-id orders.
Fix: keep is_listed as a derived column, or migrate all 5 sites to is_institutional (inverted) in the same PR; add them to the blast-radius; gate behind the money-path Pest suite.
CRITICAL

2. Every Acharya card crashes at §1-F — no "why-notes" exist for the 3 streams

The spec scopes engine work to benchmarks.py only. But build_21task_scorecard always calls section1f_abilities() (assemble.py:188), which raises KeyError if the stream — or any of its 15 abilities — has no authored "why this matters" note. Those notes exist only for the 7 student streams. First Acharya card → KeyError → teacher stuck "preparing". This needs 15 notes × 3 streams of Sutirtha content — not in the data we extracted, and unowned in the PRD.
Fix: author the notes (and check §5/§6 content) before any generation; add ability_notes.py to the change-set; extend the existing stream-specificity test to the 3 streams so the gap fails in CI, not in front of a teacher.
CRITICAL

3. "Single saffron benchmark" mechanism doesn't exist — collapsing 3 layers to 1 crashes every consumer

Grep for benchmark_mode = 0 hits. Every consumer hard-unpacks the 3-layer tuple (dev,champ,comp = …). Encoding one value → crash on the first card. The only non-crashing option is a 3-tuple with the champion value repeated — but then the render still draws three identical benchmark bars, so the promised single saffron bar never appears.
Fix: commit to one contract — store internal 3-tuples (champion repeated) and add a benchmark_mode flag both the engine and the render read to draw one saffron series. Note that the shared pillar/IntelliGraph/age block must be stored in full 3-layer shape too.
CRITICAL

4. "No Career Pathways" mechanism doesn't exist — turning §7 off trips the validator

Grep for has_pathways = 0 hits. build_21task always builds §7 and seeds §8 from it (top_pathway = section7[0]). The fail-closed output gate requires §7 (validate.py, which the spec doesn't list). So "skip §7" as written either crashes §8 or gets rejected (no card); leaving it on prints a career-pathway block on a teacher's card.
Fix: implement end-to-end — branch §7 off, pass a null pathway to §8 (already null-safe), make the required-sections gate stream-aware, guard the render. Add validate.py to the blast radius.
HIGH

5. The "prove zero change to the 7 streams" gate doesn't exist in CI

The spec/PRD promise a golden-master "if a single number moves, we stop" gate and name a SHA-pin + rebaseline script. Neither exists. CI just runs the test suite + a render job. The one real byte-for-byte proof (two-engine-score-parity.py) is manual and never wired in; the only assembled-card golden test covers just one of the 7 streams.
Fix: wire the parity script into CI (origin/main → PR head, all 21 student fixtures) as a required job, or delete the false claim and document the real manual procedure. Add an assembled-card golden for a second stream.
HIGH

6. Adding the 3 streams turns the existing 7-stream test suite RED

~6 guards hardcode "exactly the 7 streams" or require a top5 / a 3-tuple — invariants Acharya deliberately violates. So the change is not "additive, tests untouched." These are the same guards that caught a past benchmark-drift bug — under deadline someone will weaken them to go green.
Fix: split the guards into student streams (strict: 3-layer, top5, monotonic) vs institutional streams (single benchmark, no top5, no pathways), each with its own checks. Treat these as blast radius, not incidental.
HIGH

7. One ability name is mis-spelled in our extracted data → crash

acharya_foundation lists "Receptiveness to Feedback" (lowercase); canon is "Receptiveness To Feedback". The pillar lookup is exact-match and doesn't canonicalise → KeyError, foundation card crashes. A silent trap — the other 18 are correctly cased.
Fix: encode the canonical "Receptiveness To Feedback" verbatim; add a test asserting every Acharya ability is a valid canonical key.
HIGH

8. The refactor breaks both Acharya safety tests, and the bare-acharya vs acharya_% mismatch is a real bug

One test creates challenges with program_key='acharya' (bare) — which won't match an acharya_% family check, so educator assertions go red. The other asserts on the audience/is_listed columns being dropped. The spec never mentions rewriting the two tests that are the safety net for this exact change.
Fix: migrate both suites in the refactor PR (real stream keys, assert on the new flag); add the rewrite to the blast radius; confirm no fixture/seeder uses bare acharya.
HIGH

9. Storefront isolation is procedural, not structural — one seeder slip flips an Acharya product publicly sellable

"Cannot appear on the public store" rests entirely on every writer routing through one controller method. The DB default for is_listed is TRUE, and both columns are mass-assignable, with no observer/constraint. Any Challenge::create(), bulk import, or a dev extending the seeder → is_listed=true → instantly purchasable.
Fix: make it structural — a saving() observer (or generated column) that force-derives listing from stream family on every save; remove the columns from mass-assignment; add a test that creates an Acharya row via the seeder and asserts it's absent from the store. Also verify prod for any existing audience='acharya' rows before defaulting the new column.
HIGH

10. The deploy canary never exercises an Acharya stream — a defect ships GREEN

The deploy self-test pings stream=neet only, and its full canary skips-and-returns-SUCCESS when a fixture is absent. No Acharya fixtures exist, so Acharya is excluded entirely. Every failure in #2–#4 would surface only in front of the first paying institution.
Fix: add Acharya fixtures + config mapping, and make the self-test ping at least one Acharya stream (or iterate all mapped streams).

2 · Should-fix (medium)

  • "No data migration" is wrong — dropping the two columns is a schema change; rename to "no data backfill" and author the migration with a tested rollback.
  • A second hardcoded catalogue copy exists in CheckoutController (comment says "6", lists 7) — replace with the single-source constant; do not union the institutional keys.
  • Spec mis-cites the audience gate — isAcharya() doesn't exist; the real gates are 4 inline string comparisons. Re-derive the read-site list from grep.
  • Pace + onboarding must key on stream family, not the institutional flag — else a future Corporate stream inherits the teacher path (or falls to the student path) silently.
  • Config program_map is a required, unlisted edit — and the two builders disagree on a missing map (one fails closed, one silently uses the raw key). Align both.
  • No stream×tier gate — a tier-5/15 request on a top5-less Acharya stream crashes. Add a typed error (institutional = tier 64 only).
  • The single benchmark mixes two layers — pillar values are the corporate champion layer, but the IntelliGraph zones (0/0/20/80) are the competitive layer. Have Sutirtha confirm intentional (this is an extra scorecard question beyond the ones already closed).
  • "All 64 assessed → 15 priority" isn't engine-enforced — an expired task can still render "not assessed". Add a coverage assertion or restate as conditional on completion.
  • The parity proof aborts once Acharya fixtures exist (old engine rejects unknown streams) — make it skip streams the old engine doesn't know.
  • "One reversible switch" has no toggle — there's no feature flag; add one config gate over admin visibility + engine mapping (mirror the institutional-consent config-gate pattern).

3 · Gaps in the spec itself (design holes)

  • The two core mechanisms (benchmark_mode, has_pathways) are presented as done flag-flips but are wholly unimplemented.
  • The §1-F why-notes, §6 library and §5/§8 content are omitted from the engine change-set — real Sutirtha content, unowned.
  • The output validator, the 5 money-path guards, the config map, and the test-suite rewrites are all missing from the blast-radius table.
  • The schema migration is denied under "no data migration".
  • No feature flag / single kill switch backs the "reversible" claim.
  • The "no live acharya challenge in prod" assumption is load-bearing and unverified.

4 · What the auditors verified as SOUND

  • #1408 is genuinely merged to main.
  • Every failure is fail-closed — no wrong card can ship silently. (The headline reassurance.)
  • The store scopes are the real gate and filter correctly — the isolation logic is right; only its durability against future writers is the concern (#9).
  • The 7 student streams' benchmark numbers are locked to the source-of-truth file — raw drift would be caught.
  • The parity tool genuinely proves same-input → same-score byte-for-byte — it's just not wired into CI (#5).
  • §8 already tolerates a null pathway — the §8 half of #4 is a small change.
  • The seeder deliberately never seeds institutional programs — the catalogue discipline exists.
  • The #1408 re-band doesn't break the existing count tests.
