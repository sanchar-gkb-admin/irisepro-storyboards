Product & Business Requirements

Stream & Scorecard Authoring

iRisePro / YASHHO · v1 draft · for KMM, Sutirtha, Goutam

TL;DR. A new stream — teacher programme, corporate, government, college — will be created by cloning an existing one and modifying it, entirely in a UI, including its scorecard, edited section by section, with a live preview and a safe publish. The bar is a Zero-Blip New Stream Rollout: stress-free for whoever authors it, error-free for the system — a new stream goes live without a single disruption to anything already running. Mission Acharya (3 teacher streams) proves the model; this is the plan to get there.

1 · Why

Our catalogue is growing past students — Mission Acharya (teachers) is live; Corporate, Government, Colleges, MSMEs and CSR follow. Each is a "stream" with its own audience and scorecard.

Today, launching a stream is an engineering project: the rubric owner authors in a Google Doc, an engineer transcribes it into code, wires the onboarding, and deploys. Slow, bottlenecked, and it won't scale to a fast-growing B2B catalogue.

2 · The product — an authoring tool built on clone & modify

You never start from a blank page. You pick an existing stream that's close, clone it, and change only what differs. The clone inherits a proven, valid, already-passing scorecard — so authoring is fast and safe.

1ClonePick a template ("Mission Acharya — Class 5–10") → Clone into a draft.
2ModifyEdit the scorecard section by section + the stream settings.
3PreviewSee the real card update live as you edit.
4PublishValidation + canary render + approval → live, versioned, rollback-able.

5 · In scope now — family-aware admin enrolment

The first shippable step (design approved) is the admin enrolment experience becoming family-aware — one guided flow that adapts to who's being enrolled (a school's students · teachers · one student · demo), instead of three disconnected screens. Storyboard: admin enrolment walkthrough. This also closes gaps we found: institutional streams were unreachable from two of the enrolment doors, and the school was never captured.

6 · The bar — a Zero-Blip New Stream Rollout

This is the promise the whole design is built to keep: adding a stream disrupts nothing. It has two halves.

Stress-free — for whoever authors it

  • You clone a proven stream, never start blank — so you inherit a valid, already-working base.
  • A guided, section-by-section flow shows exactly what's left; you can't forget a piece.
  • A live preview means no guessing — you see the real card before anyone else does.

Error-free — for the running system

  • Isolation — a new (or edited) stream cannot affect any existing stream. Existing cards, enrolments and money paths are provably untouched.
  • Completeness gate — can't publish until every ability has a benchmark + note and every section is filled.
  • Live canary render — the real scorecard is generated and rendered before go-live; a broken card can never ship.
  • Approval + versioning — a sign-off before live; every version kept, one-click rollback if anything looks off.
  • No downtime — a stream goes live as data, not a code deploy.
Zero-Blip is an engineering commitment, not a slogan. A lot of infrastructure sits under it — validation, isolation guarantees, canary rendering, golden-output checks, versioned publish/rollback — detailed in the companion Engineering Design. Two safety invariants are absolute and hold at every phase: a minor's data is never processed without valid guardian consent (one source of truth: date of birth) already hardened, and an institutional / admin-only stream can never be sold on the public storefront.

8 · Success metrics · non-goals

  • Time to launch a stream: engineering-weeks → hours (Phase 2) → self-serve minutes (Phase 3).
  • Zero deploys to add a stream within an existing family; zero children's-data / money-isolation incidents.

Non-goals: a generic form/rules engine; auto-generating benchmark numbers (they stay expert-authored, just entered in the tool); changing the public storefront or payments.
