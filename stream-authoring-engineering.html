Engineering Design

Zero-Blip New Stream Rollout

Companion to the Stream & Scorecard Authoring PRD · engine + Backend · v1 draft

Thesis. "Add a stream = clone-and-modify data, live in minutes, zero disruption" is achievable because the platform already carries most of the machinery (registries, family shapes, a two-engine parity gate, a golden-output freeze, a deploy canary). This doc inventories what exists, the gap to full data-drive, and the engineering that closes it — organised around the five Zero-Blip guarantees.

1 · The five Zero-Blip guarantees (and their machinery)

① IsolationA new/edited stream cannot change any existing stream's output. Enforced by the two-engine score-parity gate (scripts/two-engine-score-parity.py, origin/main→HEAD, additive-only allow-list) + the Golden invariance freeze (tests/Golden/ScorecardInvarianceTest.php byte-asserts frozen baselines).
② CompletenessCan't publish an under-specified stream. Today: engine fail-loud (ability_notes.py KeyError on a missing §1-F note; ScorecardInputBuilder throws SC_UNKNOWN_STREAM). Target: the same invariants as author-time validation.
③ Canary renderThe real card is generated + rendered before go-live. Today: scorecards:selftest is a deploy gate (deploy.sh:448,533) + hourly scorecards:delivery-canary. Gap: neither sweeps per-stream (see §3).
④ Versioned publish / rollbackToday streams live in version-controlled config → PR + rollback. Target: a versioned stream-definition record so a published stream can be rolled back like config.
⑤ No downtimeStream = data, not a code path. Engine already branches on data markers (has_pathways, benchmark_mode), so a stream ships without new branches. Feature-flag (features.institutional_streams) gates a whole category off/on with no deploy.

2 · Current architecture — the ~70% spine (what's already data)

  • Stream registry — SellableChallengeSeeder: PROGRAMS / INSTITUTIONAL_PROGRAMS / ONBOARDING_FAMILY / TIERS, consumed everywhere (form, validation, E2E guard) — never re-hardcoded.
  • Onboarding shape — OnboardingFamily::SHAPES turns manual / profile-fields / board / pace / consent into data; the 4 readers (OnboardingService, OnboardingDiff, Enrollment::availableModes, MobileStudentController) read the shape, no per-family if.
  • Category predicates — Challenge::isInstitutional()/onboardingFamily()/isEducatorStream() derive from the registry, no stored/drifting flags.
  • Engine data markers — assemble.py/validate.py branch on prog.get("has_pathways")/benchmark_mode; §7 suppression, single-vs-triple benchmark, output gate all key off data. benchmarks.py::_institutional_stream() is a factory (a new band = one call).

5 · Target architecture

  1. One stream registry as the source of truth — a versioned record per stream: identity (program_key, label, tier, listing), family, onboarding shape, enrolment field-spec, and a reference to its scorecard definition. Everything else derives; nothing enumerates streams independently.
  2. Section-keyed scorecard store — today's benchmarks.py / ability_notes.py / section6_content.json reorganised into a per-stream, per-section authorable store (the section editor's backing model). The engine reads it exactly as it reads the current data files.
  3. Consent as data — consentPolicy() wired into the gate; a family's basis (by-age / self / institution-attested) is honoured, not hardcoded.
  4. Reframing as data — per-family wording travels in the engine payload; the render applies a generic sweep. Enables new families + Kannada with no template edit.
  5. Field-spec as data — profile_fields carries type/label/validation/column; drives the enrol form, request validation, and storage. Boot-time assertion: every declared field maps to a real column.
  6. Integrity choke — EnrolmentService::enrol() enforces referential + family + institution + tier invariants for every door.

7 · Risks

  • Consent rewiring touches the DPDPA/WORM path — behind the existing institution_attested_enabled-style flag, with golden tests (a self family never triggers guardian requirement; a by_age minor still does).
  • funding_source enum widening (employer billing) collides with "tracked revenue = razorpay only" (Enrollment::scopeTrackedRevenue) — any new value must be explicitly classified.
  • Field-spec ↔ column coupling — a shape can name a field with no column; guard with a boot-time assertion.
  • New tier/task shapes — validate.py keys "7-task-capable" off top5 and tier off _TIERS={5,15,64}; the tier universe must become data before a differently-shaped stream (e.g. a 2-tier corporate) ships.
